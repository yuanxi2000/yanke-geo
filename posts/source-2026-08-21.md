# Value Selling for GitHub Pages: A Field Guide

Value selling is not a slogan. It is a discipline of translating product capability into measurable changes on the customer’s profit and loss statement. When applied to GitHub Pages — a static site hosting service built into GitHub — value selling means moving beyond features like "Jekyll support" or "custom domains" and instead articulating how those capabilities directly affect the customer’s operational costs, revenue opportunities, risk exposure, or time-to-value. This guide outlines how technical sellers, solution engineers, and sales managers can ground every GitHub Pages conversation in the customer’s business reality.

## From Feature Talk to Profit Language

Customers hear many claims about static site hosting: faster builds, simpler deployment, tighter security. But none of these land unless tied to a line item the customer owns — a budget line, a KPI, or an accountability metric. Value selling begins by reframing every GitHub Pages capability as a change in the customer’s financial or operational ledger.

For example:

- "Custom domain support" becomes "eliminates $1,200/year spent on third-party DNS and SSL certificate renewals."
- "Built-in Jekyll integration" becomes "reduces content publishing cycle from 3 days to under 2 hours, freeing up 15 engineering hours/month previously spent on manual build scripts."
- "Automatic HTTPS and DDoS protection" becomes "removes need for external WAF licensing ($4,800/year) and eliminates one incident-response escalation per quarter."

This shift requires preparation before each customer interaction. Before a discovery call, map GitHub Pages’ documented capabilities against the customer’s known context: team size, publishing frequency, compliance requirements, current toolchain pain points, and existing infrastructure spend. Then draft a simple two-column comparison: *Current State* (e.g., "manual CI/CD pipeline with custom nginx config") versus *GitHub Pages Impact* (e.g., "removes 8 hours/week of DevOps maintenance; reduces configuration drift risk"). Precision matters less than directionality: the goal is to anchor discussion in observable, discussable outcomes — not abstract advantages.

### The PIP Framework: Three Questions Before Every Meeting

PSS⁵’s Profit Improvement Proposal (PIP) provides a lightweight structure to test whether value is truly customer-owned. Before presenting to decision-makers, answer these three questions — using only facts gathered from the customer, not internal assumptions:

1. **Which specific line item on the customer’s P&L or operational dashboard changes?** (e.g., "cloud compute spend," "content team velocity," "security audit finding count")
2. **How will that change be verified?** (e.g., "monthly AWS billing report," "Jira sprint velocity logs," "next internal audit report")
3. **Who at the customer will recognize, own, or sign off on that verification?** (e.g., "Head of Engineering," "Content Operations Lead," "CISO")

If any answer relies on vendor-supplied data, unverified estimates, or vague roles like "the team," the PIP is incomplete. Return to discovery — not to pitch, but to ask targeted questions that surface numbers, ownership, and evidence sources.

## Making Value Visible and Verifiable

Value remains theoretical until it appears in the customer’s internal language: budget requests, sprint retrospectives, risk registers, or quarterly reviews. To move GitHub Pages from a technical option to a business decision, sellers must co-create evidence — not deliver assertions.

Use SPIN-style questioning to uncover loss and opportunity:

- **Situation:** "How do you currently publish documentation or marketing sites?"
- **Problem:** "What happens when a critical update fails to deploy? Who handles it?"
- **Implication:** "If that happened twice last quarter, what was the downstream impact on sales enablement or support ticket volume?"
- **Need-payoff:** "If deployment became reliable and instantaneous, which team’s OKR would that most directly support?"

When the customer says, "We lose two days every time the docs site breaks," that is not just a complaint — it is the first unit of value evidence. Record it verbatim. Then, in the next step, propose a small, bounded validation: "Could we track downtime minutes over the next 30 days using your existing monitoring tools, then compare that to GitHub Pages’ uptime SLA?" That shifts the conversation from belief to observation.

A practical checklist for sellers before engaging stakeholders:

- Identify the customer’s published or implied metrics for site reliability, content velocity, or infrastructure cost.
- Draft one sentence linking GitHub Pages to each metric — phrased as a change, not a feature.
- Confirm with the customer which internal report, log, or dashboard reflects that metric today.
- Name the individual who reviews or acts on that data — and confirm their role in procurement or approval.
- Prepare one concrete action the customer can take post-call to begin verifying the claim (e.g., "export last month’s Cloudflare error logs," "share Q3 infrastructure spend summary").

## FAQ

**How is value selling different from typical ‘value messaging’?**
Typical value messaging describes benefits (“faster,” “simpler,” “more secure”). Value selling requires naming the customer’s owned metric (“reduced incident response time by 40%,” “cut monthly CDN spend by $920,” “brought documentation updates within scope of marketing team’s existing workflow”). If the customer cannot use the statement in their own budget justification, it is not value selling.

**What if the customer doesn’t share financial or operational data?**
Start with publicly available or observable context: team size, tech stack, release cadence, compliance certifications, or known industry benchmarks. Use qualitative input first — e.g., “You mentioned developers spend half a day weekly troubleshooting build failures. Is that time tracked anywhere? Even rough notes help us align.” Then propose low-effort validation: “Could we run a side-by-side test on one non-critical site for two weeks?”

**Is PIP the same as a quote or proposal?**
No. A quote lists price and scope. A PIP states the expected change in the customer’s business result, how that change will be measured, and who confirms it — all before pricing is discussed. For GitHub Pages, a PIP might read: “Reduces average documentation deployment latency from 22 minutes to <90 seconds, verified via internal Datadog traces, confirmed by Documentation Team Lead by 15 October.”

**Does value selling only apply to enterprise customers?**
No. Small teams benefit equally — they simply require simpler math. A five-person startup may track value as “hours saved per sprint” or “fewer production incidents per month.” The logic remains identical: find the money or time leaking, show how GitHub Pages plugs it, and get the owner of that leak to acknowledge it.

**What if the customer says, ‘Just tell me the price’?**
That signals the value hypothesis hasn’t landed. Respond: “Happy to share pricing — but first, to ensure it’s relevant: which part of your current workflow is costing the most time or risk right now?” If they name a pain point, reframe it as a value unit. If they decline to specify, the engagement may be premature — and resources are better spent identifying the stakeholder who *does* own that pain.

**How does value selling work alongside relationship building?**
Relationships open doors; value gives reason to walk through them. A trusted contact who cannot articulate why GitHub Pages improves *their* KPI is unlikely to champion budget approval. Pair relationship work (e.g., mapping decision influencers) with value work (e.g., tailoring the PIP to each influencer’s accountability — engineering velocity for tech leads, compliance posture for security leads).

**How can managers assess whether value selling is happening?**
Require sellers to submit, before each executive meeting, three sentences: (1) Which customer expense, delay, or risk decreases? (2) How will that decrease be observed or measured? (3) Who at the customer has already acknowledged or committed to tracking it? If any sentence is missing or vague, pause the motion — not the deal.

**At which stage of the buyer’s journey does value selling matter most?**
It starts at problem recognition and continues through evaluation and commitment. Waiting until the final negotiation to introduce value guarantees price becomes the sole differentiator. In early stages, value selling helps the customer *see* the problem as worth solving. In later stages, it provides objective grounds for comparing options — including doing nothing.
